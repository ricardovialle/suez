suez vs tensorQTL

Speed, calibration and power of suez and tensorQTL (CPU and GPU), run on the same simulated repeated-measures eQTL datasets on one workstation. Both tools see the same quantile-normalized expression, the same genotypes and the same ±100 kb cis windows.

4.0x slower suez with a dense GRM kernel at N = 2,000 (8 cores) than tensorQTL on the GPU
λ 1.46 vs 0.98 eQTL test on null data with 2 samples per individual: tensorQTL on all samples vs suez
147 s on GPU tensorQTL gene-level permutations (map_cis, 10,000 permutations) for 4,000 genes, vs 503 s on one CPU thread

Summary

  • With the default (repeated-individual) kernel, suez is as fast as tensorQTL per core and faster on all 8 cores. One suez core was within 0.6-2.3x of the fastest tensorQTL run on every size from 200 to 4,000 samples. On 8 cores suez was 1.4-5.7x faster, because tensorQTL maps one gene at a time and gains little from threads or the GPU when cis windows hold only ~100-250 SNPs.
  • With a dense kernel (GRM, or a learned covariance), suez slows with N: still 1.7x faster than tensorQTL at N = 400 on 8 cores, but 2-4x slower at N = 1,000-2,000 (9-16x on one core). Step 1 (learn_covariance) adds 4-46 s at N = 200-600. tensorQTL is also about 2x faster for eQTL-only mapping (no condition).
  • The GPU pays off for permutations and large N, not for nominal scans of small windows. For nominal mapping the GPU was slower than one CPU thread up to N = 400 (per-gene transfers dominate) and about 2x faster at N = 1,000-4,000. For map_cis it was 2-9x faster. On the CPU, 8 threads were slower than 1 thread up to N = 400 (up to 10x, on M_fac3) and about 1.7x faster at N ≥ 1,000.
  • tensorQTL on all samples of a repeated-measures design is miscalibrated. Treating the two samples of an individual as independent inflates the eQTL test (λ 1.12-1.46, up to 2x the nominal false-positive rate). It also makes the response test conservative for a within-individual condition (λ 0.24-0.89), which loses power. Expression PCs do not fix either. suez stayed at λ 0.98-1.06 on every dataset.
  • The standard fix, mapping per individual (mean and difference of the two conditions), is calibrated and about as powerful as suez for a balanced 2-level design. It cannot handle 3+ levels, a continuous condition or unbalanced repeats; suez can, with one model.
  • suez's step-1 kernel matters for power: modelling the latent factors raised eQTL detection from 0.43 to 0.57 (M) and response detection from 0.50 to 0.80 (HS), compared with the repeated-individual kernel alone.

Setup

Data

All datasets come from the suez benchmark simulator (bench/sim.R, the same seeds as bench/datasets.R), plus two added for this comparison (bench/tensorqtl/datasets_tq.R). Expression = condition effect + individual effect (SD 0.5; SD 1 in NULLR) + 5 latent factors + noise; 20% of genes have a causal SNP, half an eQTL (0.4 SD per allele) and half a response eQTL (effect only in the treated or higher condition levels). Genotypes have AR(1) LD (ρ = 0.8) within each gene. G is a larger scan (4,000 genes, ~1M tests); NULLR has no cis effects at all and a strong individual effect, for calibration.

What each tool runs

  • suez (map_interaction_qtl, normalization_approach = "qq", cisdist 100 kb, no bootstrap unless stated): genotype and genotype x condition likelihood-ratio tests in the mixed model, for every cis pair. Kernel: the dataset's (repeated-individual only, or a GRM where named) for timings; for statistics also the step-1 kernel from learn_covariance(P = 10). Timed: the map_interaction_qtl call (normalization and eigendecomposition included), with a monotonic clock.
  • tensorQTL 1.0.10 (cis.map_nominal, window 100 kb): every sample is a phenotype column and its individual's genotypes are repeated. eQTL test: nominal mapping with the condition (dummies) and 5 expression PCs as covariates; response test: interaction_df = the condition, with the 5 PCs. A 3-level factor gets one Wald test per level, combined here by Bonferroni (tensorQTL has no joint test). "Per individual": the mean and the difference of the two conditions, each rank-normalized, mapped with 5 PCs of each. Timed: both map_nominal calls, including writing the per-pair parquet files and excluding data loading and CUDA initialisation (~0.2 s).
  • The PCs are computed from expression after regressing out the condition, so they capture the 5 simulated latent factors. Neither tool gets a MAF filter beyond suez's built-in rule (≥ 5 ALT alleles), so the test counts match to within 0.4%.
  • Hardware: CPU runs are pinned to 1 BLAS thread. "suez 8 cores" is 8 forked doMC workers; "tensorQTL CPU 8 threads" is torch.set_num_threads(8). Speed numbers are the median of 3 interleaved repetitions.

Why tensorQTL drifts both ways. With samples of one individual treated as independent, the genotype effect is estimated from pseudo-replicates, so its standard error is too small (inflated eQTL test). The condition contrast, in contrast, is within individuals; ordinary least squares counts the individual effect as noise, so the interaction's standard error is too large (deflated response test). A continuous condition that varies within individuals (M_num) is roughly calibrated for the response test. With one sample per individual (M_eqtl) tensorQTL is calibrated, as expected.

Power

Gene-level: a gene is called when its smallest p-value times its number of cis tests (Bonferroni within the gene) is below 0.05. "Calibrated threshold" uses instead the 5% quantile of that statistic over null genes, which removes the advantage an inflated test gets from false positives. The datasets have only 15-30 causal genes of each type, so differences under about 0.2 are within noise (one gene is 0.03-0.07).

Agreement between the tools

Spearman correlation of p-values over all tested pairs of dataset M. suez with the repeated-individual kernel and tensorQTL without PCs rank pairs almost identically: the models differ only in how the samples of an individual are weighted, which shifts the calibration but hardly the ranking. Adding PCs or the step-1 kernel changes the ranking (they remove the latent factors). tensorQTL's GPU and CPU results agree to float32 precision.

Issues found along the way

  • suez crashed with one condition on x86. In eQTL-only mode (a single condition, no covariates) the null model has no fixed columns, and grid_values multiplied a 0 x 0 triangular matrix by a 0 x S block. For more than ~50-80 SNPs per gene Eigen's blocked product divided by the zero depth: SIGFPE on 1 core, and silently 0 results with forked workers. (Apple silicon does not trap integer division, which is probably why the macOS benchmarks passed.) Fixed in src/lmm.cpp, with a regression test in tests/model_checks.R; the M_eqtl results here use the fixed build.
  • tensorQTL 1.0.10 with several interaction terms raises KeyError: 'pval_i' while summarising the top association per gene, after the per-pair files are written. The runner catches that one error and uses the per-pair files.
  • WSL2's wall clock jumps (backwards and forwards by tens of seconds), which corrupts timings based on it, including R's proc.time() elapsed. suez is timed with /proc/uptime and tensorQTL with time.perf_counter(), both monotonic.

Reproduce

From the repository root, with pixi installed (it builds R 4.4 and Python 3.11 with CUDA PyTorch in bench/tensorqtl/.pixi):

P="pixi run --manifest-path bench/tensorqtl/pixi.toml"
$P -e r R CMD INSTALL --no-docs --library=bench/lib/cur .
$P -e r Rscript bench/tensorqtl/sim_tq.R
$P -e r Rscript bench/tensorqtl/export.R S M L XL XXL G M_grm L_grm XL_grm M_fac3 M_num M_cov M_eqtl M_unbal HS NULLR
bash bench/tensorqtl/run_all.sh
$P -e py python bench/tensorqtl/analyze.py
